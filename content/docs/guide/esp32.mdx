FrameOS runs on **ESP32-S3 microcontrollers** - no Linux, no SD card, no SSH. The backend,
[FrameOS Cloud](/guide/cloud#flash-an-esp32-from-the-browser) or
[flash.frameos.net](#standalone) flashes a firmware image over USB straight from the browser, and
from then on the device renders its scenes **itself**, drives the panel, and - with a backend or
the cloud - fetches new scenes over WiFi and updates its own firmware over the air.

This is not a cut-down mode. The same scene interpreter that runs on a Raspberry Pi runs on the
S3, with the same apps, the same JavaScript runtime, the same image pipeline, and the same
assets, logs, metrics and scheduler the backend shows for a Pi frame. What a $6 board *cannot*
do is a short, specific list - it's [at the bottom of this page](#what-it-cannot-do).

<Callout title="Standalone, self-hosted backend or FrameOS Cloud">
  An **ESP32-S3** can be set up and managed from either a [self-hosted backend](/guide/backend)
  or [FrameOS Cloud](/guide/cloud). The cloud flashes the generic release firmware from your
  browser and pushes interpreted scenes. It can also run **standalone**, with no backend and no
  account: [flash.frameos.net](https://flash.frameos.net/) flashes it over USB with your board,
  WiFi and starter scenes, and its board tools change the WiFi or update the firmware later over
  the same cable - an ESP32 has no admin page of its own. The **thin-client** boards below
  can't run standalone: an ESP32-C3 is rendered for by a self-hosted backend or by the cloud,
  where it counts as one of a paid plan's [cloud-rendered frames](/guide/cloud#limits), and a
  [Pico](/guide/pico) needs the self-hosted backend.
</Callout>

<Callout title="Two kinds of microcontroller frame">
  An **ESP32-S3 with PSRAM** renders scenes on the device itself. A **PSRAM-less board**
  (ESP32-C3, and the [Pico W boards](/guide/pico)) can't hold a renderer, so it runs as a *thin
  client*: the backend renders and dithers the scene and the device streams the finished panel
  bytes. Both are set up the same way and look identical in the backend. An S3 can work the same
  way by choice - see [rendering on the server](#render-on-server).
</Callout>

## What you need

- **An ESP32-S3 board with PSRAM.** Rendering happens in PSRAM, so don't skip it. 8&nbsp;MB is
  enough for every supported panel, including the 13.3" 1600×1200 six-color ones - the render
  canvas is 16-bit and a 13.3" scene fits in 3.7&nbsp;MB ([details](#performance)).
  The reference bare board is the
  [Seeed XIAO ESP32-S3](https://www.seeedstudio.com/XIAO-ESP32S3-p-5627.html?sensecap_affiliate=NK0JMuC&referring_service=link)
  (8&nbsp;MB flash, 8&nbsp;MB octal PSRAM), but most people start from an
  [all-in-one board](#supported-boards) that already has a panel attached.
- **A panel**: any Waveshare-family SPI e-paper panel, wired over SPI, the 10.3" IT8951 panel,
  one tiny I2C OLED, the touch LCDs of the [SenseCAP Indicator](/devices/seeed-sensecap-indicator),
  the [Sunton ESP32-8048S070](/devices/sunton-esp32-8048s070) and the
  [Guition ESP32-4848S040](/devices/guition-esp32-4848s040), the round AMOLED of the
  [Waveshare ESP32-S3-Touch-AMOLED-1.75](/devices/waveshare-esp32-s3-touch-amoled-1in75), the LCDs
  of Elecrow's CrowPanel [Advance 7.0"](/devices/elecrow-crowpanel-advance-7in0),
  [Advance 2.8"](/devices/elecrow-crowpanel-advance-2in8), round
  [1.46" rotary](/devices/elecrow-crowpanel-1in46-rotary) and
  [2.01" watch](/devices/elecrow-crowpanel-2in01-watch) - or no display at all.
  The 12.48" panels use a different controller stack and still need a Pi.
- **The [backend](/guide/backend)**, [FrameOS Cloud](/guide/cloud) or
  [flash.frameos.net](#standalone), to flash the board. Nothing is compiled: all three write the signed
  [release](https://github.com/FrameOS/frameos/releases) image for your chip and flash size, then
  configure the board over USB.

## Flash the device

1. Click **New frame** in the backend and choose **Flash embedded device**.
2. Pick the platform (**ESP32-S3** or **ESP32-C3**), your hardware preset or panel, and enter
   your WiFi credentials.
3. Connect the board over USB on the **Connect over USB** card. It reads the board and offers the
   next step: **Flash FrameOS & set up this frame** on a blank board, **Set up as this frame** on
   one that runs FrameOS but isn't provisioned yet, and **Update over USB** / **Apply frame settings** later on.
4. The browser writes the published release image that matches the board's chip and flash size (it
   reads the flash id, so a 16&nbsp;MB board gets the 16&nbsp;MB layout and a 4&nbsp;MB C3 its own)
   and then sends this frame's settings over the USB console - preset, panel, pins, WiFi, backend
   address, API key, hostname, HTTP response limit and admin login. What a console line can't carry
   (an HTTPS certificate, service keys, the schedule) arrives with the first settings sync over
   WiFi. Nothing is compiled, so a first flash takes about a minute. This uses Web Serial, so it works
   in Chrome and Edge, on `https://` or `localhost`. A backend served over plain `http://` from
   another machine (the Home Assistant add-on behind ingress, for instance) has no Web Serial, so
   its **Connect over USB** card opens [flash.frameos.net](https://flash.frameos.net/) in a window
   and hands it the frame: the image still comes from your backend, and the progress and the USB
   log come back to the frame's Logs panel. Every browser flasher checks the image against the
   FrameOS release signature before it writes a byte. Either USB port a board offers works: the chip's own
   *USB JTAG/serial debug unit*, or a *USB Single Serial* UART bridge like the CH340 on the Seeed
   reTerminals. Or download the image from the
   [release](https://github.com/FrameOS/frameos/releases) and flash it by hand - there is one per
   chip and flash layout (`-generic` is 8&nbsp;MB on an S3 and 4&nbsp;MB on a C3, next to `-4mb`,
   `-8mb`, `-16mb` and `-32mb`):

   ```bash
   esptool.py --chip esp32s3 --port /dev/tty.usbmodem* --baud 460800 \
     --flash_size 8MB write_flash 0x0 frameos-<version>-esp32-s3-generic.bin
   ```

The device boots fully provisioned: it joins your WiFi, registers with the backend, pulls its
scenes, and renders. It joins WPA2 and WPA3 networks (mixed WPA/WPA2 ones too); a WPA1-only
(TKIP) network doesn't connect. A frame whose WiFi drops keeps
reconnecting every 30 seconds, so a router restart doesn't strand it until the next reboot.
It always joins on a 20&nbsp;MHz channel, like a Pi, even where
the router offers 40&nbsp;MHz: a frame needs a few KB/s, and the narrow channel holds up better on
a crowded 2.4&nbsp;GHz band.

### Standalone, from flash.frameos.net [#standalone]

[flash.frameos.net](https://flash.frameos.net/) flashes and sets up an ESP32-S3 with no backend and
no account. Pick a hardware preset or a panel, name the frame, enter your WiFi, and tick the scenes
to start with: every sample scene a standalone frame can run (nothing that needs a Pi or an
account's API key), each with its picture, grouped by category with a tickbox per category and a
search. Presets fill the list for you - *A few to start*, *Interactive LCD scenes*, *Best for
e-paper*, *Everything* or *Only the Scene store* - up to what the board has room for, and say what
didn't fit. The [Scene store](/guide/scenes#frame-apps) is always in, so the frame can add more
scenes by itself later. A **Layout** select under the presets picks the
[layout](/guide/scenes#layouts) the scenes wear, each with its picture: *No layout*, the layouts
*Made for this board*, the *Desktops* and the *Full screen* ones. The reTerminal Sticky starts on
its own layout and the E1001 to E1004 on *reTerminal*. The scenes go over the cable compressed and
in batches, so even *Everything* - a hundred-odd scenes - is on a reTerminal Sticky in three to five
minutes. Your browser's time zone goes along. A board that takes taps and has
nothing marked to start on opens on the [scene switcher](/guide/scenes#input); a board of keys starts
on the first scene you picked.

Afterwards the page's board tools work over the same cable: the USB log, a new WiFi network, a
restart, and a firmware update that keeps every setting - a standalone board has no control plane
to update it over the air. The ESP32-C3 boards aren't on it: they need a backend or
[FrameOS Cloud](/guide/cloud#flash-an-esp32-from-the-browser) to render for them. The page counts,
anonymously, how often it's opened and how flashes end; nothing is kept on your computer.

### Provisioning by hand

A board flashed by hand with a release image can be configured without the backend's flasher.
Every supported panel driver is compiled into every image - you pick the panel at runtime:

- **Captive portal**: an unprovisioned device raises a WiFi hotspot called `FrameOS-XXXX`. Join
  it and any web page redirects to the setup form (WiFi, backend URL, frame ID and API key,
  panel, GPIO pins). The hotspot is WPA2-protected with a 10-character passphrase generated per
  device - it's on the setup screen, `config` prints it on the serial console, and `set ap_psk`
  changes it. Requests from inside the
  hotspot skip the admin login - the passphrase on the panel is the credential - so a forgotten
  admin password doesn't mean a factory reset to change WiFi. Until then the panel
  shows a QR code your phone joins the hotspot with, and the network's name, its password and the
  setup page's address under it - on a round panel all of it inside the circle. Once provisioned
  but without scenes, it shows the frame's name, panel, IP and who manages it. Typed into a browser
  later, the setup page of a frame with an admin login says how to open it: from the hotspot, the
  backend's **Frame setup access**, or `set admin_user` / `admin_pass` on the console.
- **Serial console** (115200 baud) - always available, and quickest for tinkering. It answers on
  both of the ports a board can bring out, the S3's built-in USB-Serial/JTAG device and UART0
  behind a USB-UART bridge:

  ```
  frameos> status                          # chip, panel, WiFi, memory, NVS use, hostname, power policy
  frameos> set hardware waveshare_esp32_s3_photopainter   # apply a board preset: panel, pins, buttons, battery wiring
  frameos> wifi MySSID MyPassword          # saves and reboots
  frameos> set wifi_ssid -                 # forget the network
  frameos> set time_zone Europe/Brussels   # IANA name; the tz data slice is fetched once online
  frameos> set panel EPD_7in5_V2
  frameos> set pins rst=5,dc=4,cs=3,cs2=-1,busy=6,sck=7,mosi=9,pwr=-1
  frameos> render                          # render right now
  frameos> mic 2                           # record two seconds and print the microphone's level
  frameos> i2c                             # what answers on the board's I2C buses: clock, charger, sensors
  frameos> set click_sounds silent         # no tap, key or loading sounds (normal turns them back on)
  frameos> ota                             # check for a firmware update
  frameos> ota downgrade                   # let the next update be an older release, once
  frameos> factory-reset                   # wipes scenes, schedule, cached data and all settings
  ```

## Scenes on a microcontroller

Install scenes exactly like on any other frame. The device syncs them from the backend as JSON
and runs them **on-device**: the same interpreter as Linux frames, with the standard apps
compiled into the firmware and code nodes, expressions and JavaScript apps running on an embedded
[QuickJS](https://bellard.org/quickjs/) (the [quickts](https://github.com/FrameOS/quickts) fork,
which parses TypeScript itself). Scene changes arrive over WiFi in seconds - no
reflashing, no compiler. A frame that stays awake keeps its JavaScript apps' interpreters between
renders while memory allows, and lets them go when a big image needs the room; a
deep-sleeping frame starts every render with fresh ones. So a module variable may or may not
survive to the next render - keep values in scene state or `frameos.remember()`
([JavaScript apps](/guide/apps#javascript-apps)).

Scenes are stored one file per scene, so a frame can hold many of them - up to 128, as many bytes
as its storage partition has room for (a reTerminal Sticky holds about a hundred) - while keeping
only the active one parsed in memory. A big set from the cloud arrives in parts, and the scene on
the panel stays until the last one is in. Each one is added, replaced or
removed on its own: the backend and the cloud send only what changed, so a push that changed one
scene of twenty writes one, and **Push & activate** has it on an awake frame's screen in a second or
two, plus the scene's own first render. A changed scene is written whole before the old one goes,
so a power cut or a full partition leaves the scene that worked. A disk chip beside the battery in
the frame's header shows how full its storage is - amber from 80%, red from 95% - and a click on it
lists the used, free and total space, the scenes' share and every scene by size. Switching scenes - from the
backend, an event, a button or the schedule - loads the new one and drops the old. A scene that
ran the board out of memory is skipped at the next boot - the frame starts on the next scene
instead of looping.

**Every built-in app works** except two that need a real operating system: *Chromium screenshot*
and *RTSP camera snapshot*. [Video](/guide/scenes#video) needs a Pi too. Calendars, weather, Home Assistant sensors, OpenAI text and images,
Immich, Google Photos, Unsplash, Wikimedia Commons, QR codes, charts, SVG, gradients, splits,
zoom/pan - all of it runs on the microcontroller, over TLS, straight from the device.

### Any-size images, natively

This is the part people don't expect from a microcontroller: **you can point an ESP32 frame at a
4000×3000 photo and it just renders it.** No proxy, no resize server, no "please host a smaller
version".

A naive decode of that JPEG needs 48&nbsp;MB of pixels - roughly six times the PSRAM on the
board. FrameOS never materialises it. The decoder scales *while* it decodes, straight into the
panel-sized canvas: a rolling window of compressed bytes goes in, correctly box-filtered target
rows come out, and the peak cost is the canvas plus a few hundred kilobytes. The
bytes go from the socket into the decoder directly - the file is never held in PSRAM or written to
flash at all. It works for baseline JPEG, PNG, WebP, BMP and PPM, and it applies to the whole chain
- a rotation or a resize downstream tells the decoder how few pixels it actually needs before a
single byte is fetched. A progressive JPEG is decoded in strips, so it fits an 8&nbsp;MB board
too, even on a 13.3" panel: read from the SD card it streams like the
rest, and off the network its body is buffered first. GIFs are buffered whole, spilling to the SD
card when they don't fit.

A huge photo is honest work, not a stall: a decode that keeps consuming its download renews the
render's time limit as it goes, up to 15 minutes, and logs its progress with an ETA - a
60-megapixel camera JPEG takes about seven minutes on an S3, and then it shows. A
short WiFi drop in the middle of a download doesn't fail the picture either: the request waits
up to 20 seconds for the link to come back, and an image the network cut short is streamed once
more.

There's a whole page on how this works and why it matters:
[Big images on small devices](/guide/images).

## Assets and the SD card

Boards with a TF/SD slot mount it at `/srv/assets`, and it behaves like the assets folder on a
Pi:

- Downloaded images are cached there instead of being re-fetched (and re-paid for) every render.
- Browse, upload, rename and delete files from the frame's **Files** panel in the backend or the
  cloud.
- The **Local image** app plays files or folders straight off the card.
- Downloads that have to be held whole - a progressive JPEG, a GIF, anything that isn't an
  image - spool to the card's `.cache` folder when they don't fit in memory, and the frame streams
  them from there. The only ceiling is the frame's
  [HTTP response size setting](/guide/settings#http-response-size) (4 MiB by default; raise it
  for big sources). Without a card, whatever is free in the frame's internal storage stands in -
  about half a megabyte on a typical 8 MB board, more on 16 or 32 MB flash, nothing on 4 MB.
  Baseline JPEGs and PNGs don't need any of this: they decode straight off the socket.
- A `.ttf` dropped into `fonts/` on the card shows up in the editor's font picker for that frame;
  **Sync fonts** copies the backend's font store over in one go. See [Fonts](#fonts).

Boards without a card slot work fine - the cache and the spool degrade to memory, and nothing
starts failing that used to work.

The free space in the board's own flash is a second place for files, **Internal storage**, beside
the card. The **Files** panel switches between *TF card* and *Internal storage* on a frame that has
both (one without a card shows its internal storage alone), and so does the *Files* scene on the
frame; scenes like *Books* and *PDF viewer* read from both.

On the reTerminal E-series the TF slot shares the panel's SPI bus: the
card takes its turns between panel refreshes, and an empty slot is reported as empty. The
[SenseCAP Indicator](/devices/seeed-sensecap-indicator)'s slot belongs to its second chip, out of
the ESP32's reach, so it keeps assets in 1&nbsp;MB of its own flash instead: room for a handful of
photos, with file names of 28 characters at most.

## Fonts [#fonts]

The firmware carries one typeface (Ubuntu Regular), read a glyph at a time where it lies in
flash. It also draws with every font on the SD card: the frame lists `fonts/*.ttf` on the card
through `GET /api/fonts`, the editor's font picker offers them, and the renderer reads each file
**in place** - no face is parsed into memory, so a scene can use as many as it names, in the Text
app, in JSX (`font-[Family_Name]`) and in SVG `<text>` alike. A name the card doesn't have draws in
the built-in face. Upload them through the **Files** panel or use **Sync fonts**, which skips files
the card already has. CFF, WOFF and variable fonts need converting to TrueType first
(`tools/font_for_card.py` in the repo). The *Fonts* sample scene shows what the card holds, and
its **Get fonts** view downloads more straight onto the frame from a catalog of 205 families
(Google Fonts' most popular Latin ones, and FrameOS's own), a style at a time, without a computer
in between.

`NotoColorEmoji.ttf` on the card gives color emoji, read from the card when drawn and kept at
their drawn size, as on a Pi.

## Updates, control and telemetry

- **Over-the-air updates**: A/B partitions with automatic rollback - if a new build fails to come
  up, the next reset boots the previous one. The device checks the backend daily, or on demand,
  and verifies the image's signature against the FrameOS release key before switching to it - the
  backend and the cloud both relay the published release for the board's own flash layout, never
  a build of their own. It refuses a release older than the one it runs
  unless you arm `ota downgrade` on the console. A sleeping frame
  stays awake for the download, logs its progress, and gives up on a release after three failed
  attempts rather than re-downloading it on every wake. A dropped connection resumes from the byte
  it stopped at, every failure says what it was (`timeout`, `closed`, `http 404`…) and at which
  byte, and the verdict reaches the backend or cloud even though the board restarts right after.
  An update waits for a render in progress rather than fighting it for
  WiFi and memory, and the image must carry the version its signature was made for. (The
  4&nbsp;MB flash profile has no OTA slot; those boards update over USB.)
- **Deploys and update progress**: the backend's deploy drawer has three buttons for an ESP32 -
  **Deploy scenes & settings**, **Deploy new firmware** and **Deploy both** - and both control
  planes show a running update on the frame's card: *updating firmware 42%*, *rebooting into
  2026.10.19*, *update failed* with the device's reason, or *already on 2026.10.19, nothing to
  install*.
- **A real HTTP API on the device**: `GET /status`, `/image`, `/state`, `/states`, and
  `POST /event/<name>` to dispatch any event into the running scene, plus logs, metrics and asset
  routes under `/api/frames/<id>/` - much the same surface the
  [Pi's local API](/guide/api) exposes ([every route](/guide/api#esp32)). Native HTTPS turns on after the frame's first settings
  sync, when it has a certificate to serve, and then the plain port 80 closes. A page from another
  site can't make the frame change anything, and ten wrong logins in five minutes shut the login
  for five minutes. After each render the frame also pushes its picture to
  a self-hosted backend, so the backend has a sleeping frame's image without pulling it. Every
  route except `/ping` needs the frame's API key or its admin login; firmware
  before 2026.10.21 answered a request without them with *Authentication required* but still
  carried it out, so update a frame on an older release.
- **Settings on the frame itself**: on a touch board, the scene settings you swipe down for have a
  gear that opens the frame's own page - the Wi-Fi network (with a scan and *Other network…*) and
  its password (an eye beside it shows what you typed), the rotation, the
  [scale](/guide/settings#render-scale), the date and time when it's offline, the battery and the
  signal, **Check for updates** and **Install update**, **Update scenes** when the store has newer
  versions of the frame's scenes, **Tap and click sounds**, **Brightness** on a screen that can dim
  and, on a frame that deep-sleeps, **Stay awake after a press or tap**, and **Render again**,
  **Restart FrameOS** and **Reboot**. **Service keys** opens a page for the keys the apps use -
  OpenAI, Unsplash, Home Assistant, Immich, GitHub - typed on the frame itself, and an **About**
  card at the end says what the frame runs on: chip, board, display, memory, storage, uptime, its
  network and who manages it.
  A frame nobody manages yet adds **Link to cloud** and **Link to backend**
  ([connecting from the frame](/guide/settings#connect-from-the-frame)); a managed one has
  **Unlink**. An update installed there gets the same
  signature checks as one from the backend or the cloud. A frame you change there tells its
  control plane its new rotation and scale. Turn the page off with
  [Frame settings on the screen](/guide/settings#on-screen); `set settings_unlock 1` on the USB
  console brings it back whatever the control plane says.
- **Logs and metrics** stream to the backend, and the last 128 lines are kept in a ring buffer on
  the device, readable over the serial console when the network is down. When the backend doesn't
  answer, the frame keeps its lines and tries again once a minute instead of waiting out a timeout
  at every step of a render.
- **An on-device scheduler**: per-scene render intervals plus minute/hour/weekday schedules that
  switch scenes, fire events, or restart/reboot the device (a **Maintenance** entry in the
  Schedule panel), evaluated on the device in the frame's
  [time zone](/guide/settings#time-zone). The
  JavaScript `format()` helper follows the frame's time zone too. The wait between
  renders counts from when the render was due, so a scene that renders every second does so every
  second, not every other one.
- **Buttons**: GPIO buttons (the board presets know where they are, and which
  [role](/guide/buttons) each one plays) reach scenes as `button` events - a `press` the moment
  the key comes up, and a `longPress` once it's been held a second, while it's still down - and raw
  `gpio` `down` / `up` edges
  ([details](/guide/scenes#input)), so a press can change a scene, re-render, or run anything you
  wire up in the editor. Every edge is timestamped by the button task, so a tap made during a
  30-second panel refresh is still a tap, and a 30&nbsp;ms debounce catches quick double taps.
  Change the button map in the frame's settings; the board picks it up on its next
  settings sync and restarts. What a press does whatever scene is showing - the next scene, say -
  is a [button action](#button-actions).
- **Button beep**: boards with a buzzer - the Seeed reTerminals - click when a press registers and
  click lower on the release, a held key sounds once, at the second its long press comes, so you
  know when to let go, and a press the board had no room for sounds a dull "no". **Button beep
  GPIO** and **Button beep tone (Hz)** sit under the frame's GPIO buttons; on the console it's
  `set buzzer_pin`, `set buzzer_tone_hz` and `beep` to test. The Waveshare
  PhotoPainter and 13.3E6 play the same notes on their speaker, and the CrowPanel 2.01" watch on its
  vibration motor. **Tap and click sounds** set to
  *Silent* mutes the clicks and the loading chirp on any board that makes them.
- **Status LED**: the reTerminal E-series' green LED lights with every note the buzzer plays, so a
  frame with its buzzer switched off still shows a press, and it stays lit while the
  [voice chat](#voice-chat) listens. **Status LED GPIO** sits next to the
  beep settings; `led` on the console tests it.
- **A cloud frame with a backend set too**: `set backend` on an enrolled frame's console (a bench
  setup) hands its content to that backend, so the frame turns down the cloud's scenes and settings.
  `status` and the cloud's frame page say so, and
  [handing it back](/guide/cloud#moving-between-cloud-backend-and-standalone) takes one button
  over USB.

## Button actions [#button-actions]

Every board's keys follow the same standard - Action, Next and Prev, Back, Home and Screen, each a
press and a hold, with no double presses, and two keys pressed together as Back on a board without
one - and [Buttons](/guide/buttons) lists what each board's keys do out of the box, the CrowPanels'
crown and knob included. A key pressed on a dark screen only turns it on, as a touch does.

**Settings → Button actions** says what a press does on this frame, whatever scene is showing:
the next or previous scene, a render, a particular scene, the display on or off, the
[voice chat](#voice-chat), the scene switcher or scene settings, or Back and Forward, on both
control planes. On a touch screen an edge swipe can be bound the same way. A press bound there
never reaches the scene. A row can also be a double or triple press, and only a key bound that way
waits for the next press. A board whose map nobody changed follows its preset, so a firmware
update brings the newest map with it; a map you changed is kept. A scene
written for other keys - a store scene that listens for
`A` and `B` - can be told which of your frame's keys are its `A` and `B` with **Map buttons** in
the installed scene's menu, without touching the scene ([details](/guide/scenes#input)). The
frame's status screen lists every button with the action it's bound to.

## Voice chat [#voice-chat]

Hold the frame's voice key for a second and talk to it: *"show the
weather"*, *"put a photo of a lighthouse on"*, *"make the text bigger"*. The buzzer plays a short
rising sparkle and the status LED lights while the frame listens; let go and it answers. What you
said streams to your backend or FrameOS Cloud while you're still talking, is transcribed there
with OpenAI's `gpt-4o-mini-transcribe`, and goes to the same AI chat the workspace has, with this
frame in its context and a small set of tools for it: switch scenes, set a field of the scene
showing, redraw, rotate the frame, show a picture, play a photo album, or have the scene AI build
a new scene or change the one showing. The audio isn't kept once the answer is in.

While it works, the panel says what's happening over the last picture - transcribing, what it
heard, each tool as it runs, and how long it's been when a turn takes more than 15 seconds (the
scene AI building a scene takes a minute or more). That's on an LCD and on the fast e-paper of the
Sticky and the E1003. The answer is drawn across the bottom of the panel for 30 seconds - what was
heard, in quotes, and the reply - and a tap on it, or a key, takes it off. It lands in the frame's
chat in the workspace too, with a log of what each sentence did. The buzzer sounds the outcome: three rising notes when something was done, one low note when
nothing was heard. It's one conversation per frame, so a follow-up like *"no, the other one"*
knows what the last sentence did. A sentence can be up to 30 seconds long.

- **Which boards**: the reTerminal E1001 and E1002 (hold REFRESH), the E1003
  (REFRESH), the reTerminal Sticky (the Action key), the Waveshare PhotoPainter (KEY1) and 13.3E6
  (BOOT) through their codec's microphones, the round AMOLED (BOOT), and Elecrow's CrowPanel 2.01"
  watch (the crown) and Advance 2.8" (BOOT). The E1004 has no microphone; a PDM microphone on its J2
  header works once **Microphone GPIO** in Settings names its pins. A Pi frame can't do this yet.
- **Which key**: the Action key held ([Buttons](/guide/buttons)), or any
  [button action](#button-actions) set to *Voice chat*, always on a long press - the frame listens
  while the key is held and stops when it's let go. Hold another key with it and it's not the voice
  chat: two keys together are Back.
- **What it may do**: four switches under **Settings → Buzzer, LED and microphone → Voice chat
  may**: *Change settings*, *Use installed scenes*, *Create new scenes* and *Access photo albums*,
  all on until you switch one off, so "show a picture of a chicken" works out of the box. A picture or scene made by voice lands on the
  frame as a preview, never on its saved list: the scene list shows it with **Install** and
  **Discard** ([preview on frame](/guide/scenes#push-activate-preview)).
- **What it needs**: the OpenAI key the AI chat uses - **Settings → OpenAI** on the backend; your
  own key or the shared one on the cloud, and a frame on WiFi with a backend or the cloud to talk
  to. Held without them, the key says on the panel what's missing and how to set it up. The
  **Voice chat** switch in Settings turns the microphone off altogether, and frames without a
  microphone don't show any of these controls.

## LCD and touch [#lcd]

The [SenseCAP Indicator](/devices/seeed-sensecap-indicator)'s 4" 480×480 color touch LCD, the 7"
800×480 of the [Sunton ESP32-8048S070](/devices/sunton-esp32-8048s070), the 4" of the
[Guition ESP32-4848S040](/devices/guition-esp32-4848s040), the round 1.75" AMOLED of the
[Waveshare ESP32-S3-Touch-AMOLED-1.75](/devices/waveshare-esp32-s3-touch-amoled-1in75) and
Elecrow's CrowPanels - the [Advance 7.0"](/devices/elecrow-crowpanel-advance-7in0) and
[Advance 2.8"](/devices/elecrow-crowpanel-advance-2in8), the round
[1.46" rotary](/devices/elecrow-crowpanel-1in46-rotary) and the
[2.01" watch](/devices/elecrow-crowpanel-2in01-watch) - bring a fast screen to the ESP32. That changes what a microcontroller frame can do:

- **Animation.** A scene whose render interval is under a second runs back to back: the store's
  *DVD Logo Bounce*, written in JSX, moves at about 29 frames a second, and the board's talk with
  the backend - scenes, settings, commands, logs and the picture - runs on a task of its own
  meanwhile. The scene draws straight into the LCD's own frame buffer, and only the part of the
  picture that changed is drawn again.
- **Touch.** The touch glass of these boards, the [reTerminal Sticky](/devices/seeed-reterminal-sticky)
  and the [E1003](/devices/seeed-reterminal-e1003) reaches scenes as the same `pointerDown`,
  `pointerMove`, `pointerUp`, `tap`, `doubleTap`, `longPress` and `swipe` events a Pi's
  touchscreen sends ([details](/guide/scenes#input)), and two fingers on the E1003 or the Sticky
  make a `pinch`. A swipe in from the screen's edge is the
  frame's: out of the box on every touch board it's the
  [scene switcher, the scene settings, back and forward](/guide/scenes#input), or whichever
  [button action](#button-actions) you bind. A touch on a dark screen only turns it on. Build touch
  interfaces with [JSX and Tailwind classes](/guide/apps#jsx-uis), which have fields with a keyboard
  on the screen: on the SenseCAP Indicator a tap on a JSX home panel is back on the glass in about
  85&nbsp;ms, and the element under your finger is shaded the moment it lands, before the scene
  answers. A touch board - an LCD, or the touch e-paper of the Sticky and the E1003 - boots straight
  into its scenes and joins WiFi in the background, so it never opens the setup hotspot by itself
  and never holds its first picture for the network. Flashed with nothing picked to start on, it
  opens on the [scene switcher](/guide/scenes#input) as its home, and a scene picked there is the
  one it boots into next. The Indicator's glass tracks one finger, and the keyboard
  on the screen still types both keys when two thumbs overlap. On touch e-paper only the changed part of the panel is
  refreshed while you tap, a switch to another scene included. The frame counts how worn each spot
  of the glass is, and a full refresh clears the ghosts once a quarter of it has changed over, or
  one spot has been rewritten sixteen times (a digit in a clock) - every fifth page of a book on
  the Sticky; a frame left alone cleans only glass that's due. `hover:` and `active:` are not drawn
  (each would cost a refresh), but the status LED lights while a press is answered and a button
  whose answer is slow is inked at once. A press held until something shows still counts as a
  click, and with **Touch beep** on, a press that something takes clicks at once, before the
  picture can answer.
- **Display on and off.** *Display on*, *Display off* and *Display on/off* switch the backlight,
  and nothing renders while it's dark. Over HTTP they're the `turnOn`, `turnOff` and `toggleScreen`
  [events](/guide/api#esp32). A key, a touch or a swipe on a dark screen only turns it on.
- **Brightness.** On the round AMOLED and the CrowPanel watch, rotary and Advance 2.8", **Power**
  sets the screen's **Brightness**, and **Dim when idle** lowers it to **Dimmed brightness** after
  so many seconds without a tap, a key or a turn of the knob. The next one brings it back at once
  and still does what it does, and dimming costs no render
  ([settings](/guide/settings#power-and-battery)). The frame's own page has a Brightness bar too,
  set on the glass as your finger moves.
- **Slow renders.** A scene switch or a refresh that hasn't put its picture up within 200 ms shows
  three pulsing dots until it does. One that answers a tap, a swipe or a key waits 500 ms, so a UI
  that answers in a few hundred milliseconds never flashes them - and an animation that takes a
  second or two to draw its next scene after a swipe shows them too.
- **Pixel scenes.** The *Pixel toys* and *Color cycling* samples compute every cell in JavaScript
  and hand it over in the [8-bit palette mode](/guide/apps#javascript-apps): Hellfire runs at 26
  frames a second at 8&nbsp;px cells, the other effects at 13 to 19. A tap or a key moves to the
  next one, and a footer along the bottom has Previous, Next, the frame rate and Hide.
- **Windows.** A [desktop layout](/guide/scenes#windows) runs two scenes side by side on an
  8&nbsp;MB board, four on a bigger one, and a window behind the one in front runs at most every
  five seconds. On the Indicator's 480×480 screen a desktop set to *Automatic* shows one scene,
  since there's no room for two.
- **Storing scenes.** While a push writes scenes to flash, an RGB LCD shows the FrameOS mark and
  *Updating*: a flash write stops the chip from refreshing the screen, so the picture would tear.
  The new scene replaces it when it's stored. The round AMOLED keeps its own picture and needs
  neither.
- **Round screens.** On the round AMOLED and the CrowPanel 1.46" rotary the switcher, the
  settings, the frame page, the keyboard and the edge swipes keep inside the circle, and scenes can do the same
  ([round screens](/guide/scenes#round-screens)).
- **Boot.** The FrameOS mark shows on black while the board starts, with a line saying what it's
  waiting for (*Connecting to Wi-Fi*, *Updating firmware*, *Starting*), and an LCD renders as soon
  as WiFi is up rather than waiting for the clock. A frame whose setup hotspot is up shows a QR
  code your phone joins it with, and the password and address under it.

## Battery and deep sleep [#power]

This is where a microcontroller frame beats a Pi. Configure it under the frame's **Power**
settings, or on the console:

| Setting | What it does |
| --- | --- |
| `deep_sleep` | Power the chip down between refreshes and cold-boot for the next one |
| `deep_sleep_on_battery` | Only sleep while running on a battery; stay connected on USB power |
| `wake_schedule` | Align wakes to wall-clock boundaries in the frame's time zone, so a clock or calendar updates *on* the hour |
| `wake_check` | Wake at least this often to pick up queued commands, without refreshing the panel |
| `battery_pin` / `battery_divider` | Read cell voltage on an ADC1 pin; percentage shows in the backend |
| `battery_enable_pin` | The GPIO that switches the divider on for a reading, on boards that gate it (`-1` = always on) |

Without `wake_schedule` the time already spent awake - boot, WiFi, render - is subtracted from
the interval, so the cadence doesn't drift by however long the render took. A pass that outlasts
its interval doesn't reboot straight into the next one: a deep-sleeping frame rests at least as
long as the pass ran, so it works at most half the time, and logs `render:overrun` to show the
scene is too slow for its interval. Below 3% battery the
frame skips the refresh and sleeps for six hours rather than cycling a flat cell into damage - and
it takes two readings a moment apart and two passes in a row to believe it, so one noisy ADC
sample can't park a healthy cell in the six-hour sleep.

**Input keeps it awake.** After a button press or a tap, a deep-sleeping frame stays up for five
minutes (**Stay awake after a press or tap** under Power, and on the frame's own page), so the next
one is answered at once instead of waking it again, and it sleeps as soon as that window closes.
Pulling out the USB cable, or switching the frame on with its power key, counts as a press:
someone has it in hand.

**It shows that it sleeps.** On e-paper with a fast refresh - the Sticky and the E1003 - a frame
going to sleep puts a small moon in the top-right corner. A tap or a key that wakes it turns the
moon into a loading ring at once, with a quiet chirp, until the scene is up: about nine seconds on
a Sticky.

**Buttons wake the frame.** Every GPIO button on a wake-capable pin is armed as a wake source
next to the timer, and so is the touch glass where the board keeps its touch controller powered
through the sleep (the Sticky and the round AMOLED; the E1003 wakes on its keys). A press brings the frame up early and reaches the scene like any
other press - held, it's a `longPress` - and that
pass renders, so "next photo" works on a sleeping frame. A press made while a battery frame is
still rendering holds the sleep for one more pass instead of being lost. While
asleep the WiFi radio is in modem sleep, the clock is kept by the RTC (no time-sync wait on wake),
and the log queue and the battery reading are flushed to the backend or cloud before the chip
halts, so a battery frame's history is complete.

The backend and the cloud both know when a frame is sleeping: right before it halts, the frame
announces when it will be back, and the frame list shows **asleep · wakes in 5 min** (or
**overdue** when the wake never came) instead of a stale "last seen", and its image carries a
small moon badge. Battery frames show their
charge in place of the status dot. Click it for a popup with charge, voltage, how often the frame
wakes, drain per day, a two-week history with a forecast to empty, and a slider that shows the
battery life at another wake cadence. The status says **Charging**, **On USB**, **Full** (only on
USB, from 98%) or how the cell is doing. A lone reading far below its neighbours is an ADC misread,
not a discharge: the frame reads the cell in rounds and reports the value it
believes, and the charts leave the rest out and say how many misreads they ignored. On the 13.3"
E1004 the Spectra 6 refresh is about 30 s of each cycle, and dithering and packing the picture for
it about 4 s; the rest is the scene's own render.

**Nothing is lost to a sleep**, on both control planes. What you ask of a
sleeping frame - a scene switch, new state values, a render, a preview, a reboot, a firmware
update, a deploy - waits in the frame's command queue on the backend or the cloud, and the frame
drains it at the start of its next wake, before it renders, so the change shows on that wake. A
queued command lives until past the announced wake. Each scene's state is kept in a file on the
device, so a value set from the control page survives the deep sleep instead of lasting one
render, and a frame awake on USB is nudged to pull at once.

The board presets carry the battery wiring - the PhotoPainter and 13.3E6 headers, the Seeed
reTerminals' switched divider, the XIAO ePaper boards, the TRMNL and the XTEINK X4 (only the
E1004's is verified on hardware so far) - and the [reTerminal E1004](/devices/seeed-reterminal-e1004)
preset also switches on `deep_sleep_on_battery` with a 15-minute `wake_check`, so it sleeps on its
5000&nbsp;mAh cell and stays connected on USB out of the box. A frame provisioned before its preset
knew the wiring keeps `battery_pin -1` until you re-run `set hardware` on the console or fill in the
three values under **Power**.

The reTerminal E-series also carry a charger and a clock chip, which FrameOS reads. With USB plugged in the charger says so, and the frame never counts as on battery -
so it doesn't deep-sleep on your desk - and the metrics show whether the cell is charging. The
clock sets the time on a cold boot, before WiFi is up, and every time sync writes it back. The
[reTerminal Sticky](/devices/seeed-reterminal-sticky) has a fuel gauge instead of a divider, which
reports the charge itself, and the [PhotoPainter](/devices/waveshare-esp32-s3-photopainter)
reads its cell and its charging from its power chip, and powers its audio chips and panel down
before each deep sleep.

A `wake_check` wake only picks up commands: the render stays when it was scheduled, so a photo set
to change once a day changes once a day, even on a frame whose clock was never set. The battery
popup shows what the frame does beside what it measures - **Re-renders every …** (the showing
scene's refresh interval) and, while it sleeps, **Checks in every …** - and the cloud's Power panel
shows the board preset's sleep settings where you set none of your own.

**Processor speed** under Power picks the chip's clock. By default an e-paper board renders at
240&nbsp;MHz and waits out the refresh at 160, and LCD and touch boards run at 240; or pick either
([settings](/guide/settings#power-and-battery)). The same setting on a Raspberry Pi picks its CPU
governor.

## Rendering on the server [#render-on-server]

An ESP32-S3 can hand its scenes to its control plane: set **Render scenes** under Power to *On the
backend* or *On FrameOS Cloud*. The backend or the cloud runs the scene in the same WebAssembly
runtime as the browser preview, dithers it to the panel's palette, and the frame downloads the
finished picture. The frame keeps WiFi, its schedule, its keys and touch, its panel and its deep
sleep, and stops doing the scene's work - no JavaScript, no image decoding, no fetches to the
scene's data sources - so a battery frame's wake is WiFi, one request and the refresh.

- **Nothing changed, nothing done.** When the picture is the one the panel shows, the frame skips
  the download and the refresh. A sleeping frame's next picture is drawn just before it wakes,
  with the scene's clock set to the wake, so the wake is a download.
- **Keys, touch and the schedule keep working.** What they would have told the scene goes with the
  next download, so a press answers in a second or three. On grey and black-and-white panels only
  the parts that changed are sent: a key typed on the E1003 is a few kilobytes.
- **The scene still decides when it renders.** Its refresh interval reaches the frame - at least
  10 seconds on a backend, the plan's floor on the cloud, and at least a minute on a Spectra 6 or
  7-color panel, so a fast scene can't keep its 15-30 second refresh going nonstop. A press, a
  scene switch or a value you set still shows at once.
- **It runs where the plane is.** On a backend a scene reaches what the backend reaches, its LAN
  included. On the cloud it reaches public addresses only. Either way it can't read the frame's
  own assets or SD card yet; a [photo album](/guide/photos) works.
- **What it costs.** Nothing on a backend. On the cloud the frame counts as one of your plan's
  [cloud-rendered frames](/guide/cloud#limits), with a five-minute floor on its interval.
- **The board holds nothing a scene does.** It's sent one empty scene, no service keys and no
  scene state.

This is how the thin-client boards (ESP32-C3, Pico) always work; on an S3 it's a choice you can
undo at any time. The frame changes over at its next render.

## How fast is it? [#performance]

Slower than a Pi, and mostly irrelevant - the panel is the bottleneck either way. Measured on the
7.3" Spectra 6 PhotoPainter board (8&nbsp;MB PSRAM), rendering *Weather*, the heaviest sample
scene:

| Step | Time |
| --- | --- |
| Cold-boot scene load + JS transpile | ~3.3 s (once, at boot) |
| SVG rasterisation | 7-8 s |
| Dither + pack to the Spectra 6 palette | ~3.2 s |
| Panel refresh (the panel's own hardware) | ~29 s |

Simpler scenes are much quicker; a black/white panel dithers and refreshes in a fraction of that.
A frame that updates a few times an hour, or a few times a day on battery, never notices. Text
with an outline takes under half a second on a 480×480 scene.

Memory on the same board: 7.1&nbsp;MB PSRAM free with a scene resident, 4.2&nbsp;MB still free at
the worst point of a render. If a panel is too large for a board's PSRAM, the backend says so
before you flash rather than leaving you with a frame that can't render.

The scene canvas is claimed once from PSRAM before WiFi starts and reused for every render. Its
format is decided by the panel first:

- **A grey or black-and-white panel draws in one byte per pixel.** Grey levels need no color, so
  an 800×480 black-and-white canvas is 384&nbsp;KB instead of 1.5&nbsp;MB. A sixteen-grey panel
  draws in four bits, in its controller's own layout, so the
  [E1003](/devices/seeed-reterminal-e1003)'s 1872×1404 is 1.3&nbsp;MB and goes to the panel as it
  is.
- **A color e-paper panel draws in 16-bit RGB565.** An 800×480 canvas is 0.77&nbsp;MB instead of
  1.5&nbsp;MB, and pixie's fast paths for it apply. The canvas dithers its stores so gradients stay
  smooth, and a photo dithered to Spectra 6 lands the same palette within 0.05% per color of a
  full-color canvas. Where the canvas and a panel buffer beside it would take more than half the
  PSRAM - a 1200×1600 panel on an 8&nbsp;MB module, the
  [reTerminal E1004](/devices/seeed-reterminal-e1004) - the picture for the panel is packed into
  the start of the canvas itself, which is what lets it render on-device at all; everywhere else it
  gets a buffer of its own, so the next render doesn't wait for the glass. The dither and the pack
  run on both cores.
- **An LCD draws straight into its own 16-bit frame buffer**, so there's nothing to copy or pack.

The Pi, HDMI and the browser preview keep a full RGBA canvas.

## Wiring

Default pins target the XIAO ESP32-S3 (a board preset overrides all of these):

| Signal | GPIO | XIAO label |
| ------ | ---- | ---------- |
| CS     | 3    | D2         |
| DC     | 4    | D3         |
| RST    | 5    | D4         |
| BUSY   | 6    | D5         |
| SCK    | 7    | D8         |
| MOSI   | 9    | D10        |

Remap at runtime with `set pins rst=5,dc=4,cs=3,busy=6,sck=7,mosi=9,pwr=-1` on the serial
console, in the captive portal, or per-frame in the backend. The 13.3" Spectra 6 panel has two
controllers and needs `cs2` as well.

## What it cannot do [#what-it-cannot-do]

Straight, so you can decide before you buy:

- **Panels**: Waveshare-family SPI e-paper, the 10.3" IT8951, one small I2C OLED, and the LCDs
  of the SenseCAP Indicator, the Sunton and Guition boards, Elecrow's CrowPanels and Waveshare's
  round AMOLED only. No
  HDMI, no other LCDs, no Pimoroni Inky HATs, no Python-backed drivers. The 12.48"
  multi-controller panels need a Pi.
- **Two apps are missing**: *Chromium screenshot* and *RTSP camera snapshot*. Both need to launch
  a real program on a real OS.
- **No video.** The [video scenes](/guide/scenes#video) play through ffmpeg on a Pi; the store
  doesn't offer them to an ESP32.
- **No Nim app editing.** Scenes run [interpreted](/guide/scenes#execution), like everywhere else.
  You can write and fork apps in **JavaScript/TypeScript** and use JS code nodes, but editing an
  app's Nim source means compiling, which means a Pi. The backend warns you when a scene contains
  Nim, and offers **Convert to an interpreted scene** to port it to JavaScript.
- **Fonts come from the card.** One built-in typeface, plus TrueType files and color emoji from
  the SD card ([Fonts](#fonts)); other formats need converting first.
- **No on-device admin web app.** The frame answers the HTTP API and serves a setup page, but the
  full `/admin` panel and the control page with the QR code are Pi-side. Manage ESP32 frames from
  the backend. (`GET /status` does report the chip, the hardware preset, and internal heap and
  largest-block figures - useful when a thin client runs out of memory.)
- **It's slow.** Seconds per render on e-paper, not milliseconds. On the SenseCAP Indicator's LCD a
  simple animation runs at about 29 frames a second and a tap answers in under a tenth of a second,
  but that's still no Pi 5 at 60.
- **PSRAM is the ceiling.** No PSRAM means thin-client mode, where the backend has to be reachable
  at render time.

## Raspberry Pi or ESP32? [#raspberry-pi-or-esp32]

| | Raspberry Pi | ESP32-S3 |
| --- | --- | --- |
| Displays | [120+ drivers](/devices): e-ink, HDMI, LCD | Waveshare SPI e-paper and eight boards' LCDs, every driver in one image |
| Video | [Plays it](/guide/scenes#video), hardware-decoded on a Pi 0-4 | - |
| Voice | - | [Hold a key and talk](#voice-chat), on boards with a microphone |
| Custom code | JavaScript, or Nim in a compiled scene | JavaScript/TypeScript |
| Apps | All of them | All but Chromium screenshots and RTSP |
| Fonts | Any TTF you upload, emoji fallback | Built-in typeface, plus TTFs and emoji on the SD card |
| Power | ~1 W, wall-powered | Deep sleep between refreshes - battery is viable |
| Updates | SSH / Remote deploys | Signed OTA with A/B rollback |
| Price | ~$15-20 (Zero 2 W) | ~$6-10 (bare S3), or an all-in-one board |

In short: pick the Pi for the broadest hardware and the deepest customisation, and the ESP32 for
a battery-powered, self-contained frame - or because you already own one of the
[all-in-one boards](#supported-boards). Want to help port a panel? See the
[firmware README](https://github.com/FrameOS/frameos/tree/main/embedded/esp32) and say hi on
[Discord](https://discord.gg/9dT9y7EzUw).
